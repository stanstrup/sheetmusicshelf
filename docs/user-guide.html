Sheet Music Shelf Handbook

A self-hosted catalogue for sheet music: it reads your PDFs, guesses what each one is, tells you how sure it is, and hands the uncertain ones to you.

01What it is

Sheet Music Shelf catalogues a pile of PDFs into something you can search by composer, form, instrument and key, and open on a phone on the sofa. Think Calibre-web or Audiobookshelf, but for scores.

Three ideas shape everything else:

  • A file is not a catalogue entry. One PDF can hold sixty pieces; one piece can span several PDFs. The thing you browse is a piece — a page range inside a file — and pieces that are the same music are grouped into a work.
  • Every guess carries a confidence. Nothing is asserted as fact because a filename looked promising. Confident guesses are filed; unsure ones wait for you in a review queue.
  • Your decision is permanent. Once you accept a value, no later scan, signal or enrichment run can argue it down.

There is no machine-learning model inside the service and no call to a language model at catalogue time. Everything is deterministic scoring over signals that can be pointed at. External tools can curate through the API, but nothing hidden is happening on your NAS.

02Getting it running

Three containers: the web app, a worker that does scanning in the background, and PostgreSQL. The compose file lives at Z:\docker\compose\sheetmusicshelf.yml, with its build context in Z:\docker\build\sheetmusicshelf.

  1. Fill in the secrets. Edit Z:\docker\compose\.sheetmusicshelf.env:

    SMS_SECRET_KEY=<long random string>
SMS_OIDC_CLIENT_ID=<from authentik>
SMS_OIDC_CLIENT_SECRET=<from authentik>
SMS_CONTACT=you@example.com

    Generate the key with python -c "import secrets; print(secrets.token_urlsafe(48))". Set the database password in .sheetmusicshelf-db.env to match.

  2. Create the authentik application — an OIDC provider plus an application, with the redirect URI pointing at your base URL. Copy the client id and secret into the env file.

  3. Start it.

    cd /mnt/z/docker/compose
docker compose -f sheetmusicshelf.yml up -d --build

    The app is on port 8014. Schema migrations run automatically at start.

SMS_CONTACT has no default and nothing works without it. MusicBrainz and IMSLP require a reachable contact — an email address or a project URL — in the User-Agent of every request, and block clients that omit one. Rather than send a fake one, the app refuses to make any outbound lookup at all until you set it. Cataloguing, browsing and reading work fine without it; only the enrichment features stop.

What gets mounted

Only two paths on the NAS, which is the whole point of the design:

HostIn the containerWhy
Z:\Books\SheetMusic/library/managedThe library. Every catalogued file lives here.
Z:\Books\SheetMusicIngest/library/ingestThe drop folder. Files here are imported and removed.
named volume/cacheRendered pages and extracted text — thousands of small files, so not on the SMB share.

Your original music folder is not mounted. Once material is in the library, where it came from stops mattering.

03Getting music in

Two routes in, for two different situations.

The drop folder, for a handful of files

Put PDFs into Z:\Books\SheetMusicIngest and run:

sms ingest              # shows what it would do
sms ingest --apply      # catalogues, files, and empties the folder

Each file is read, catalogued, copied into the library under a composer-and-title folder, and then deleted from the drop folder — the same way Calibre empties its auto-add directory. Nothing is deleted until the library holds a copy of the same size, and --keep skips the removal if you would rather tidy up yourself.

A collection, for a whole set at once

A collection is a directory of music that shares a naming convention — a CD-ROM rip, a downloaded archive. Registering one lets a purpose-built adapter read the convention instead of guessing:

sms collection add "The Sheet Music Archive" /path/to/archive
sms collection scan 2
sms collection materialise 2 --apply

scan reads and catalogues; materialise copies the files into the library. Originals are copied, never moved or modified.

Adapters

An adapter knows one collection's conventions. Four ship with the app — for the CD Sheet Music discs, the Sheet Music Archive, a filename-based pop collection, and a generic fallback that reads PDF metadata and outlines. sms adapters lists them; the right one is detected automatically when you scan.

04How the library is arranged

Calibre-style, and readable without the app running:

Z:\Books\SheetMusic\
  Wolfgang Amadeus Mozart\
    Fantasia in F Minor (K. 608)\moz2.pdf
    Minuet in D Major (K. 355-576b)\k0355.pdf
  Edvard Grieg\
    Concerto in A minor\Edvard Grieg - Concerto in A minor.pdf
  _Books\
    CD Sheet Music Mozart\works\mozvol2.pdf

A folder name is built from metadata, so correcting a piece in review moves its file to match, and the folder it emptied is cleaned up. You will see files relocate as you review — that is working as intended, not a bug.

_Books\ holds volumes containing many pieces. A 378-page anthology cannot sit inside one work's folder without misrepresenting itself, so it keeps its original relative path.

05Browsing and filtering

The front page is the catalogue, with facets down the side: composer, form, instrument, key, period, collection and review state. Filters combine, and the counts update with them.

Each card previews the piece's own first page — not the file's — so a piece buried on page 212 of an anthology still shows the right thing.

A composer page collects everything by them, with a portrait and dates pulled from Wikidata. A work page shows every copy you hold, links out to IMSLP and MusicBrainz, and lists movements in order when the work is one file per movement.

06The review queue

After a scan, every piece has a confidence between 0 and 1 and sits in one of three bands:

≥ 0.80 Accepted Filed without asking. Signals agreed and were strong.
0.50–0.79 Needs review A plausible reading that wants a human glance.
< 0.50 Held Too little to go on, or signals that contradict each other.

Signals that disagree cap confidence at 0.45 regardless of how strong they are, so a conflict always reaches you rather than being averaged away. The thresholds are per-collection, so a messy folder can be made stricter than a well-organised one.

/review shows the least confident piece first — worst guesses first, because that is where your attention changes the most. The ← and → arrows (or the arrow keys) move through the queue without deciding anything, which is how you skip past one you cannot judge yet.

The four actions

Accept
Records your values as decisions. No later signal can outvote them and a re-scan will not disturb them. The piece leaves the queue.
Skip
Changes nothing. The piece stays in the queue and comes round again, behind the rest.
Not music
For a cover page, a licence, a scan of something that is not a score. Set aside and excluded from the catalogue, but kept so you can find it again.
Delete
Removes the entry for good and remembers the page range, so a re-scan cannot recreate it.

In every case the PDF itself is untouched. "Delete" removes a catalogue entry, not a file.

07Reading and annotating

Pages are rendered to WebP on the server at four widths — 320, 800, 1200 and 1800 — and cached by content hash, so a re-scan of an unchanged file reuses them and an edited file gets fresh ones automatically. Most of this library has no text layer, so server-side rendering is the only thing that works everywhere.

The reader opens at the piece's first page, not the file's. On a phone it fetches pages as you need them rather than pulling a 50 MB scan before showing anything.

Annotations are stored per page in normalised 0–1 coordinates, so a mark made on a phone lands in the right place on a tablet. A screen-wake helper keeps the display on while you are playing.

This is a networked application. Offline use was ruled out by design — it assumes you are on the LAN or a VPN. There is no local cache of scores on the device.

08Shelves and personal notes

Shelves are hand-made collections in the Calibre sense: "Christmas", "learning now", "for the recital". A piece can sit on any number of them, and a shelf keeps its own order so you can sequence a programme.

Separately, each piece carries a small fixed set of personal fields — difficulty, status, rating, free notes and tags. These are yours and are never touched by scanning or enrichment.

09Books holding many pieces

When one PDF holds an anthology, the adapter tries to find the individual pieces from the outline, the table of contents, or embedded metadata. When it gets the boundaries wrong, /split/<file id> is a page-range editor: adjust where each piece starts and ends, add one that was missed, remove one that is not really there.

Ranges you delete are remembered, so a later re-scan will not recreate an entry you already rejected.

10Composers, dates and links

Three enrichment passes, all optional and all requiring SMS_CONTACT:

sms composer enrich     # portrait, dates and period from Wikidata
sms work enrich         # IMSLP and MusicBrainz links, matched on catalogue number
sms work years          # composition year, read from the IMSLP page already linked

Links are only attempted for works with an accepted copy, so a guess never comes back wearing a citation. Where the automatic match is wrong or missing, the work page has a search box: pick the right result by hand and it is marked confirmed, after which automatic runs leave it alone.

Matching handles the awkward cases — MusicBrainz files Mozart's first sonata as "K. 189d/279" and IMSLP as "K.283/189h", and either half of a compound citation counts.

Every outbound request passes through a rate gate with a circuit breaker: roughly one MusicBrainz request per 1.2 seconds, and if the service starts refusing, the app stands down instead of hammering it. Enrichment is slow on purpose.

11The API, for agents

External tools curating the catalogue are a first-class client, not a workaround — the API exists so a language model running outside the service can do the tedious identification work that the app deliberately does not.

sms token create "curation bot" --scope curate

The plaintext token is shown once and never stored. Present it as a bearer token against /api/v1:

EndpointPurpose
GET /piecesSearch and filter the catalogue
GET /facetsAvailable filter values with counts
GET /curation/summaryWhat still needs attention
GET /curation/pieces/{id}Everything known about one piece, with every signal
POST /curation/pieces/{id}/approveRecord values as decisions
POST /curation/pieces/{id}/rejectSet a piece aside
GET /pieces/{id}/pages/{n}A rendered page, for a model that can see
PUT /pieces/{id}/annotations/{n}Replace one page's marks

An agent can also add a candidate rather than a decision — an opinion with a weight, which the scorer then weighs against everything else. That is usually the more honest thing for a machine to do.

Interactive documentation is at /docs when SMS_DEBUG is on.

13Things that will catch you out

Review one collection at a time

A thousand pieces in one queue is not reviewable. Filter the queue by collection and finish one before starting the next.

Files move when you correct them

Folder names come from metadata. Accepting a corrected title relocates the file and prunes the empty folder. Do not keep external links straight into the library tree.

The worker yields to the rest of the machine

SMS_LOAD_CEILING pauses scanning between files while the one-minute load average is above it. On a small box running dozens of containers, a scan that ignores load is not a slow scan — it is an outage for everything else.

Scanning over SMB is slow because of hashing

--no-hash skips SHA-256 and is much faster, at the cost of the app not noticing that a file changed underneath it.

A "book" is decided by piece count

A file with more than one piece is filed under _Books\. If a merged or multi-movement file lands there unexpectedly, it is because something split it into several pieces — fix the pieces and re-run materialise, and it will move.

Run sms verify after anything that moves files

Copying and filing are not covered by the database transaction, so a run that fails part-way leaves the rows rolled back and the moves done. It reports and never fixes, so it is safe to run any time.

Deleting is about the catalogue, not the disk

Nothing in the app deletes a source PDF. The strongest thing a delete does is remove the library copy, which materialise can rebuild.
