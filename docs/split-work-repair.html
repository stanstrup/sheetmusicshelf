The Sheet Music Archive files long works as one PDF per part. Fifteen of them are now one file each — and the reasoning that decided which fifteen mattered more than the merging did.

The problemA concerto catalogued as three concertos

grieg/con_amin/ holds conamin1.pdf, conamin2.pdf and conamin3.pdf. That is one concerto in three movements, and the catalogue had it as three separate concertos — three entries to open in turn, with no way to play through the piece.

Fixing the grouping was the easy half and was done earlier: fourteen archive folders that name a single work are now listed by hand in the adapter, so their files share a title and fold into one work. But the files were still separate. This repair joins them.

Step 1Which multi-file works are actually split

69 works held more than one file. Merging all of them would have been badly wrong — a work has several files for at least four different reasons, and only one of them wants merging.

split
One file per movement or section, in sequence. 15 works — merge these
editions
The same piece twice from different sources: cnoc27_2.pdf (6pp) and noct27_2.pdf (5pp), both Nocturne Op. 27 no. 2. leave alone — merging would print the same music twice
arrangement
k401-2h.pdf and k401-4h.pdf — the same fugue for two hands and for four. leave alone — different music to play
misgrouped
maz_a.pdf and maz_b.pdf, two different mazurkas that both ended up titled just “Mazurka”. leave alone — a grouping fault, not a split

The test used is deliberately strict, and leans on a judgement already made rather than inventing a second one: the adapter must have marked every file as part of a split work, all the files must come from one folder of one collection, none may be named as an alternate take ((v2)), and the parts must fall into an order with no ties.

Everything else was left exactly as it was. Bach's Well-Tempered Clavier alone contributes 18 works to the “leave alone” pile: each number has both a pre&fugN.pdf holding prelude and fugue together and a preludN.pdf holding only the prelude. Joining those would have duplicated every prelude in the set.

Step 2Establishing the order

The filenames give the order, except where they don't. Liszt's first concerto is filed as lispc1_a, liszpc1b, lispc1c, liszpc1d — the stem is not even spelled the same way from one part to the next, so sorting on the filename interleaves them wrongly. The trailing letter is the real sequence.

None of these PDFs carry any metadata at all — no title, no subject, nothing — so the claim had to be checked against the scans themselves. Rendering the top band of the first and last page of each part shows the publisher's printed page numbers:

The ordering rule that came out of this: a movement number wins when the filename ends in digits; otherwise a trailing letter orders the parts; and a part with neither sorts first — which is what correctly puts the overture ahead of act one in Mozart's Magic Flute.

One work was checked page-by-page rather than by numbers. Brahms's Violin Concerto has three movements but four files, which looked wrong until the pages were rendered: it is one continuous Carl Fischer edition (violin and piano, edited by Leopold Auer) cut into page ranges. File 1 opens with the title page and file 3 begins the Adagio, but the cuts are not movement boundaries. The parts are chunks, not movements — so the merged file's bookmarks are labelled with the part they came from rather than claiming to be movements.

Step 3The pages that appear twice

Mozart's K. 537 gave the game away: the last page of part mzk537_c is the same page as the first of mzk537d. The archive repeats, at the top of each part, the page on which that part begins, so that every part opens as a self-contained score. Any naive merge inherits those duplicates.

So every join was compared before anything was joined — a small greyscale render of the last page of each part against the first page of the next, scored by mean absolute difference. These are scans, so two renders of the same page are near-identical but not bit-identical; the gap between “same page” and “next page” turned out to be wide enough to be unambiguous.

work 1418 · Mozart, Piano Concerto no. 26

mzk537d last | mzk537_e first diff = 41.35 ok
mzk537_e last | mzk537_f first diff = 34.93 ok

Genuine seams scored 25–45. Duplicates scored 0.00, with one exception: the Goldberg Variations seam scored 3.11, close enough to the threshold to need looking at. Rendered side by side, gb_var1 page 3 and gb_var2 page 1 are plainly the same page — both end with Var. 2, Allegretto beginning — and the 3.11 is scan noise. A threshold of 6.0 separates the two populations cleanly.

Ten repeated pages were found and dropped. Six of them were in the Christmas Oratorio alone.

Step 4Merging, ingesting, and a setback

Each work was joined in playing order, skipping the repeated leading pages, with an outline entry per part so the merged file is navigable. The fifteen files went into Z:\Books\SheetMusicIngest and through sms ingest --apply — the drop folder built earlier this session, which catalogues what it finds, files it into the library and empties itself.

Then the ingest split them all back up again. Fifteen files arrived as 118 pieces. The generic adapter reads a PDF's outline as piece boundaries, so the very bookmarks that made the merged files navigable were read as evidence that each file held many pieces — and it filed them under _Books/ as multi-piece volumes.

The bookmarks are worth keeping, so the fix went the other way: collapse each file back to a single piece spanning all its pages, and attach it to the work that already existed rather than creating a new one. Attaching to the existing work preserves its composer, catalogue number and any IMSLP or MusicBrainz link already established. Re-filing then moved each file out of _Books/ and into Composer/Title/, where it belongs.

Step 5Retiring the split versions

Three things happened to each of the 118 parts: its catalogue entry was deleted, its copy in the library was removed, and a tombstone recorded its page range so that a re-scan of the archive cannot quietly bring the split version back.

Nothing under Z:\Books\Music was touched. Those scans are the only copy that exists and the merged files were built from them. Only the library copies under Z:\Books\SheetMusic — which can be rebuilt from the originals at any time — were removed.

One work was left split. Work 1161 holds eleven files in three overlapping series — tchpc1a1 to tchpc1a6, tchpc1b1, tchpc1b2, and tchpc1c1 to tchpc1c3 — so “movement 1” names three different files and there is no single order to put them in. Whether the b and c series are a second edition, a continuation or something else cannot be told from the filenames.

It is left exactly as it was rather than guessed at. Deciding what a, b and c are is the only thing needed to finish it.

CaveatsThree things worth knowing

File deletion is not covered by the transaction

The first retirement run hit a Windows file lock — the running server still had a PDF open — and the database transaction rolled back cleanly. The unlink calls did not: nine parts processed before the lock (Franck's three and Debussy's six, alphabetically ahead of Grieg) stayed deleted on disk while their rows came back. The second run therefore reported 109 copies removed rather than 118. The end state is correct — all 118 are gone and none were left behind, verified by scanning the library for every split filename stem — but the two numbers not matching is this, not a missed file.

99 empty work records were deleted

Regrouping the split folders earlier had orphaned a lot of work rows: when 27 Goldberg entries became one work, 26 were left with no pieces. Those were cleaned up. Two of them still carried IMSLP links and composition years, which were lost — and recovered by re-running enrichment, which finished slightly ahead of where it started: 75 IMSLP and 58 MusicBrainz links, against 75 and 57 before.

The library is now the only thing that has to be mounted

This repair ran after the library was made authoritative earlier in the session, so the merges read from the library copies rather than the originals, and the merged files were filed straight back into it.

MethodNone of this is in the app

Every part of this ran as one-off scripts held outside the source tree, and the application code is unchanged by it. Which folders hold a single work is a judgement about the music — that Grieg's con_amin is one concerto while Chopin's preludes is twenty-four separate preludes, when both are “one filename stem plus a number” — and it is not something an adapter can be taught. Building it in would have meant the rule running unsupervised on collections nobody had looked at.

The scripts, in the order they were used:

  • merge_tool.py — classifies multi-file works and puts the parts in order
  • headers.py — renders the printed page numbers for checking continuity
  • contact.py — tiles the first page of each part into one strip to look at
  • seams.py — compares every join for repeated pages
  • do_merge.py — writes the merged PDFs into the drop folder
  • adopt_merged.py — collapses each merged file to one piece on the existing work
  • retire_splits.py — deletes the split entries, their library copies, and tombstones the ranges

The test suite was run at the end and passes at 256 tests, unchanged in count, because nothing in the application was touched.

Catalogue after the repair: 1,825 pieces across four collections — Mozart (85), Sheet Music Archive (1,248), pop collection (477) and Ingest (15) — in 1,330 works by 306 composers. Library 1,825 files, 876 MB.
