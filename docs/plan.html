Three collections, three completely different metadata problems

This is the finding that shapes the whole design. Guess quality is not a property of the library; it is a property of each collection. So the ingester is a set of small, per-collection adapters, not one global heuristic.

CollectionApprox.Best available signalExpected quality
CD Sheet Music/*~1,500 DocInfo /Subject carries composer, title, key, catalogue no. and page span. Plus a text-extractable toc.pdf per disc. high
The Sheet Music Archive/*~1,200 No DocInfo. Folder = composer (chopin, beethovn); filename stub encodes opus/catalogue number. medium — needs authority lookup
Sheet Music Collection/~1,000 Flat folder, NNN - Artist - Title.pdf. Popular repertoire, duplicates present ((v2) suffixes, two spellings of the same song). medium — needs dedup
Everything else~1,000 Named editions (Bach Leipzig, Schubert vols. 1–7, Liszt Exercises) — handled per-collection as you reach them. case by case

The /Subject find

Every file in the CD Sheet Music discs carries a machine-readable subject line. From Mozart - The Complete Works for Piano/works/k0001.pdf:

/Subject : "Mozart:  Minuet in G Major, K1, P1 of 1"
/Title   : "CD Sheet Music" by Stephens Publishing Company

observed variants across discs:
"Brahms:   Intermezzo, A Maj, Op118 #2, P380-383"
"Haydn:  Sonata in Eb Major, Hoboken 28, P1-12"
"JS Bach: 4 Part Chorales 300-371, P144-178"
"Brahms: SP Hungarian 9 in Emi, JBP9, P449-450"

Composer, work title, key, catalogue system and number, and the page range — already structured. One adapter with a tolerant grammar for this line resolves roughly 40% of the library at high confidence, and it is exactly the piece-and-page-range model the catalogue needs.

Junk to exclude

The discs ship software with the music: readme/ folders, 10 .exe, 6 .iso, Acrobat password crackers, PhotoScore installers, Mac resource-fork stubs. Each adapter declares ignore globs; nothing outside a declared music path is ever catalogued.

IIArchitecture, and the constraints it bends to

This lands on a 4-core NUC already carrying ~45 containers, with the library on a CIFS mount that only resolves inside the Ubuntu-24.04 WSL distro. Every choice below is made against that, not against a clean-slate ideal.

ComponentChoiceReason
API + UIFastAPI + UvicornJinja server-rendering with HTMX for the interactive bits. Best-in-class PDF tooling (pymupdf), and no Node build step to maintain.
Databasepostgres:16, own containerMatches the mealie / paperless / romm pattern already in the stack: independent backup, no shared blast radius.
Job queuePostgres-backed, no RedisScanning and thumbnailing must not block requests, but a fifth Redis on this box is not worth 100 MB. A job table with SELECT … FOR UPDATE SKIP LOCKED is sufficient at this scale.
WorkerSame image, --worker, 1 processSeparate container so a long scan can be stopped without taking the UI down. Hard-capped at 1 CPU.
SearchPostgres full-text (tsvector)A few thousand works and maybe 15k pieces. Meilisearch would be a second service for no gain.
Authauthentik OIDCAuth-code + PKCE, mirroring mealie.yml. Long-lived revocable device tokens are added in the phone phase.

Compose shape

  sheetmusicshelf-pgdata                        #   database
  sheetmusicshelf-cache                         #   thumbnails, extracted text, derived files

binds:
  /mnt/z/Books/Music:/library/source:ro         #   read-only. never written to.
  /mnt/z/Books/SheetMusic:/library/managed:rw   #   the managed tree it builds

Deliberate details

  • Source mount is :ro. The plan says copy, never move — the mount enforces it, so a bug cannot eat the originals.
  • Thumbnails go on a volume, not CIFS. Tens of thousands of small files over SMB is the same trap as SQLite-on-CIFS.
  • Port 8014 — 8010–8012 are taken by paperless, 8008 and 8002 by others.
  • nautical labels on the app and the DB, with OVERRIDE_SOURCE_DIR pointed at sheetmusicshelf-pgdata (the cache volume is regenerable).

Resource budget

  • App 512M / cpus: 1; worker 512M / cpus: 1; Postgres 256M.
  • The worker self-throttles: a scan yields between files and pauses when /proc/loadavg exceeds a configured ceiling. On this box a background job that ignores load is a box-wide outage.
  • A full library scan over CIFS is minutes, not seconds — it is a job with progress, never a request.

IIIData model

The one structural decision everything else depends on: the file is not the catalogue entry. A work is what you look for; a file is where a copy of it happens to live; a piece is the page range inside that file. Separating those three is what makes pages 380–383 of the Brahms complete edition a first-class thing you can shelve, filter and open.

TableHoldsNotes
composerCanonical name, name variants, birth/death, MusicBrainz & IMSLP idsAn authority record, so beethovn, Beethoven, L. van and Ludwig van Beethoven collapse to one entity
workComposer, title, catalogue system + number, key, year, form/genre, parent_work_idSelf-referencing: Sonata K.280 is a work with three movement-works beneath it. Catalogue number splits into system (K, BWV, Op, Hob, D) + number + suffix so sorting is numeric, not lexical
source_fileOriginal path, SHA-256, size, mtime, page count, collection, managed pathHash-keyed, so a file renamed outside the app re-links on rescan instead of duplicating
piecework × source_file + page_start, page_end, instrumentation, arranger, edition, publisher, confidence, review stateThe browsable catalogue entry. One file yields many pieces; one work has many pieces across editions
collectionSource folder, adapter name, ignore globs, ingest status, thresholdsThe unit of work — you ingest and review one collection at a time
instrumentControlled vocabulary + aliasesMany-to-many to piece with a role (solo / accompaniment / voice), so “piano four hands” and “high voice + piano” are queryable
shelf, shelf_itemUser-defined collectionsCalibre-style. Ordered, so a shelf doubles as a setlist
field_candidatePiece, field name, proposed value, source, weight, accepted-by, accepted-atThe audit trail behind every guess — see next section
app_user, annotationOIDC subject; annotation reserved for laterAnnotations stored as a layer keyed to page + coordinates, never burned into the PDF

Fixed personal fields on piece

Per your call — a defined set rather than runtime-definable columns: difficulty (1–10, nullable), status (unplayed / learning / repertoire / retired), rating (0–5), notes (free text), tags (free), last_opened. Adding one later is a migration, not a redesign.

IVIngest, and what “confidence” actually means

No LLM in this pipeline. Every number it produces is traceable to a rule that fired, which is the entire point — a confidence score you cannot explain is worse than no score, because you cannot decide what to review.

01WalkEnumerate the collection, apply ignore globs, hash each file, record page count.
02ExtractDocInfo, outline tree, per-page text where a text layer exists.
03AdaptThe collection’s adapter turns raw signals into field candidates.
04ResolveMatch composer and catalogue number against the authority cache; merge agreeing candidates.
05ScorePer-field confidence, then a piece-level score. Route to auto-accept or the review queue.
06MaterialiseCopy accepted items into the managed tree, render thumbnails.

Scoring

Each signal proposes a value for a field with a base weight. Independent signals that agree reinforce; signals that conflict cap the field’s confidence and flag it. The piece’s confidence is the minimum across its identifying fields — composer, title, page range — because a piece is only as trustworthy as its weakest identifier.

SignalBase weightFields it can propose
Parsed DocInfo /Subject (CD Sheet Music grammar)0.85composer, title, key, catalogue no., page range
PDF outline entry with a resolvable page destination0.80title, page range
Catalogue number matched in the authority cache0.80work identity, canonical title, key, year
Parent folder matches a known composer alias0.70composer
Collection-level default (e.g. the disc is solo piano)0.60instrumentation
Filename pattern NNN - Artist - Title0.55composer/artist, title
Catalogue-number regex on a cryptic stub (bwv772)0.50catalogue no.
First-page text heuristics0.35title, composer
On-demand OCR of pages 1–20.35title, composer
Routing

≥ 0.80 auto-accept  0.50–0.79 review queue  < 0.50 or conflicting — held

Thresholds are per-collection settings, not constants — you will want them stricter on the pop pile than on the CD Sheet Music discs. Nothing is ever silently overwritten: accepting a candidate records who accepted it and when, and rejected alternatives stay in field_candidate so a bad adapter can be re-run without losing your corrections.

OCR

On demand only, as agreed. No bulk pass. The review UI shows an OCR title page button on any item with no text layer; it queues a single tesseract job over pages 1–2 and folds the result back in as another weighted signal. On this hardware a background pass over the ~3,200 image-only files would be a multi-day tax on a box already at its limit.

Duplicates

Exact duplicates are free — same hash. Near-duplicates, such as 108 - Animals - The House Of Rising Sun.pdf beside 108 - The Animals - House Of The Rising Sun.pdf, or anything ending (v2), are detected by normalised-title similarity plus page count and surfaced as a possible-duplicate pair. You merge them, keep both as editions of one work, or dismiss. Never auto-deleted.

VWhere the LLM fits, without living in the app

You want to use a model for the messy parts but not ship one inside the service. That is a clean separation, and the seam is an HTTP API rather than a file export — external curation tools are first-class clients, not a workaround. built

EndpointPurpose
GET /curation/queueUncertain pieces, each with every candidate value, its source and its weight, plus which fields are missing or conflicted. You can see why a piece is uncertain before proposing anything.
GET /curation/pieces/{id}/textDocInfo, PDF outline and extracted text for the opening pages. Empty for image-only scans — the queue item says so in advance rather than making you ask.
POST /curation/candidatesPropose. Scored, not applied: agreeing with an existing signal raises confidence, disagreeing flags a conflict and holds the piece.
POST /curation/decisionsDecide. Final — cannot be outvoted by a later signal of any weight, and survives a re-scan.

Tokens are minted per tool (sms token create claude-curation), scoped, revocable, and stored hashed. The result: no API key in the container, no per-item cost baked into the product, no dependency on a model staying available — and the hard collections still get the benefit.

Verified

Round-trip tested against the live API: a proposal at weight 0.65 moved a piece from hold to review; a decision made the value final; a later contradicting proposal at weight 0.99 could not displace it; and a full re-scan of the collection left the decision intact without creating duplicate entries.

VIWeb UI and the phone

Desktop — cataloguing

  • Browse with faceted filters: composer, instrument, form/genre, key, period, catalogue system, collection, shelf, status.
  • Review queue per collection: proposed values, the signals that produced them, the page thumbnail alongside. Accept, edit or reject from the keyboard.
  • Page-range editor for the ~470 anthologies: a thumbnail strip with draggable split markers, pre-populated from the outline where one exists. This is the authoritative fallback and gets built regardless.
  • Work view: every edition and copy of a work side by side, so you can pick the good scan.

Phone — PWA

  • Same server, responsive templates, installable to the homescreen. No app store, no build pipeline.
  • Reader is PDF.js opened at the piece’s page_start, so a piece inside a 378-page volume opens on the right page.
  • Portrait single page, landscape two-up, tap zones for page turns.
  • Online-only by your call — but the reader talks to a byte-range endpoint, so PDF.js streams pages instead of pulling a 50 MB file. That is what makes it usable over the VPN.
Kept open for later

Annotation is the reason to eventually go native. Storing annotations as a coordinate layer against piece and page — not flattened into the PDF — means the native app, when it comes, inherits everything made in the browser, and your originals stay pristine. The schema carries the table from day one; nothing else changes.

VIIIFirst target, concretely

Z:\Books\Music\CD Sheet Music\Mozart - The Complete Works for Piano — 94 PDFs. It is the right first collection because it is the best-instrumented one in the library, so a poor result there means the approach is wrong, not the data.

PathTreatment
works/k0001.pdf … k0626.pdfPrimary music. The filename stub gives the Köchel number, /Subject gives title, key and page span; both must agree or the piece is held for review.
music/k279-08r2.pdf, mozk455.pdfAlternate takes and revisions with irregular names. Falls back to /Subject alone; expect these in the review queue.
toc.pdfText-extractable, structured TITLE / K. FILENAME / PGS columns under headings like Sonatas and Fantasies. Parsed as an independent second signal — agreement with /Subject is what pushes items over the auto-accept line, and its headings seed the form/genre field.
readme/Ignored by glob.

Expected outcome: the great majority auto-accepted with composer, Köchel number, title, key, form and page range; a short tail of alternates to review by hand. That tail is the real measurement — it tells us what the adapter grammar is missing before we point it at 1,400 more files.

IXRisks and open questions

RiskMitigation
audiobookshelf mounts /mnt/z/Books not an issueIt only indexes Books\_Calibre Library, so a managed tree at Z:\Books\SheetMusic does not collide with it. Settled.
The box is already at its limitHard CPU and memory caps, a single worker, load-aware throttling, no Redis, no bulk OCR, no second search engine. This service has to be a quiet neighbour.
CIFS scan latency — 3,686 files over SMB, competing with GoodSyncScanning is an incremental job keyed on mtime and size; a rescan touches only what changed. Never a synchronous request.
Adapter grammars will be wrong at firstIngest is idempotent and re-runnable: candidates are versioned by source, and human decisions permanently outrank machine ones, so re-running a fixed adapter never destroys your review work.
Docker Desktop’s bind-mount shim breaks containers on restartKnown stack issue; the repo README carries the --force-recreate-from-WSL-space recipe.

Open, and worth deciding before P2

  • Naming scheme in the managed tree — Composer/Work (Cat. no.)/edition.pdf is the proposal, but anthologies are the awkward case: a 378-page volume holding 60 pieces cannot be filed under one work. Proposal: books stay filed under their collection, and only single-work files are filed by composer.
  • Instrumentation vocabulary — start with a small hand-written list (solo piano, piano four hands, voice and piano, organ, chamber, orchestral score, lead sheet) and grow it, rather than importing a standard taxonomy you would then have to maintain.
